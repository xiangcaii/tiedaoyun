## 1. 目标与非目标

### 1.1 目标

- 落实 PRD 第 6 节 MVP 范围：数据模型 / 表单 / 列表 / 流程 / 页面 / 权限 / 审计 / 单机部署
- 给出可被 `plan` 阶段直接拆任务的技术决策
- 保留扩展点：插件、连接器、IM 适配，避免后期重构

### 1.2 非目标

- 集群模式（Kubernetes 部署）
- 模板市场 / 组件市场
- AI 辅助搭建
- 自定义组件运行时（仅预留接口）
- 移动端原生 App

> 与 PRD 第 4 节保持一致。

## 5. 数据架构

### 5.1 存储策略

`[Decision]` 每个用户定义的实体生成**独立的物理表**：

- 表名规则：`e_<app_slug>__<entity_slug>`（例如 `e_hr__expense`）
- 实体 ID 使用 UUID（应用内唯一）
- 关系字段使用外键约束，跨实体引用通过外键 + 索引
- 子表（一对多）通过独立表 + 外键实现，主表只保留主键
- 多对多通过中间表 `e_<a>__<b>__rel` 实现
- 审计字段（created_at / updated_at / created_by / updated_by / deleted_at）由 `BaseEntity` mixin 自动加

`[Decision]` 元数据表用于存储 schema 定义本身（实体 / 字段 / 关系定义），与运行时物理表分离。

### 5.2 Schema 演化与迁移

- 实体保存时通过 `data-model` 模块生成 Prisma migration
- 字段类型变更（影响已有数据）走"影响分析"流程，列出被引用位置，要求显式确认
- 字段删除默认软删（仅元数据标记 `deprecated`），物理删除走后台异步任务，30 天后可清理
- 所有迁移记录进 `app_migrations` 表，可回看

### 5.3 核心元数据表

| 表 | 用途 |
| --- | --- |
| `users` | 用户 |
| `workspaces` | 工作空间 |
| `workspace_members` | 工作空间成员（含角色） |
| `roles` | 角色（内置 + 自定义） |
| `permissions` | 权限点 |
| `role_permissions` | 角色-权限关联 |
| `apps` | 应用 |
| `app_versions` | 应用版本（dev/test/prod） |
| `entities` | 实体元数据（指向物理表） |
| `fields` | 字段元数据 |
| `relations` | 关系元数据 |
| `forms` | 表单定义（JSON schema） |
| `lists` | 列表定义 |
| `pages` | 页面定义 |
| `workflows` | 流程定义（节点 + 流转） |
| `workflow_instances` | 流程实例 |
| `workflow_tasks` | 待办任务 |
| `workflow_logs` | 流程操作日志 |
| `audit_logs` | 审计日志 |

### 5.4 动态表管理

- 启动时检查元数据表与物理表一致性，发现差异自动补齐
- 物理表操作走 `DataEngineService`，统一封装：
  - `query(entity, filter, sort, page)`
  - `create(entity, payload)`
  - `update(entity, id, payload)`
  - `delete(entity, id)`（软删）
  - `batchCreate / batchUpdate / batchDelete`
- 所有写操作经 `permission` guard，行级 / 字段级权限在此层强制
- 物理表加 GIN 索引支持 JSONB 字段检索（扩展字段场景）

## 6. API 契约

### 6.1 设计原则

- RESTful 资源命名（`/api/v1/apps/:id/entities/:eid/records`）
- 所有请求带 `X-Workspace-Id` header（多工作空间隔离）
- 响应统一包装 `{ code, data, message, traceId }`
- 错误码分类：`AUTH_*` / `PERM_*` / `VALIDATION_*` / `BIZ_*` / `SYS_*`
- 时间统一 ISO8601 + UTC，UI 层格式化
- 列表接口统一参数：`page`、`pageSize`、`sort`、`filter`（JSON）

### 6.2 OpenAPI 自动化

- 后端通过 `@nestjs/swagger` 暴露 `/api/docs`
- CI 跑 `openapi-typescript` 自动生成 `api-client` 包
- 前端禁用手写 fetch，统一通过 React Query hooks

## 7. 鉴权与权限

### 7.1 鉴权

- JWT Access Token（15 分钟，HS256）+ Refresh Token（7 天，httpOnly cookie）
- 多端登录同一账号，token 独立撤销
- 密码：bcrypt（cost 12）
- `[Hypothesis]` MVP 阶段不引入 SSO，接口预留

### 7.2 权限模型

- **功能级**（菜单 / 应用 / 设计器操作）：`role → permissions[]`
- **数据级**（行）：策略表达式 DSL，例如 `owner == currentUser` / `department in currentUser.departments`
- **字段级**（列 / 单元格）：白名单 + 角色映射，默认拒绝
- 权限在 `PermissionService.evaluate(user, resource, action, context)` 统一计算
- 所有 `DataEngine` 写操作必经 `PermissionGuard`

### 7.3 实现

- 角色与权限点静态预置 + 启动加载到 Redis 缓存
- 行级 / 字段级策略在调用时即时解析，结果可短期缓存

## 8. 流程引擎架构

### 8.1 核心抽象

- `WorkflowDefinition`：节点 + 边 + 触发器的 JSON
- `Node`：开始 / 审批 / 抄送 / 分支 / 并行网关 / 子流程 / 定时器 / 连接器 / 结束
- `Edge`：流转条件（表达式 DSL）
- `WorkflowInstance`：运行时实例，绑定 definition 版本
- `Task`：待办单元，绑定实例 + 节点 + 接收人

### 8.2 执行模型

- 状态机：实例状态（`running` / `suspended` / `completed` / `terminated`）
- 节点执行器：`NodeExecutor` 接口，每个节点类型一个实现（`ApprovalExecutor` / `NotifyExecutor` / `ConnectorExecutor` 等）
- 持久化：每步操作写 `workflow_logs`（含原值 / 新值 / 操作人 / 时间），保证可重放
- 异步：审批待办通知、连接器调用、超时检查走 BullMQ
- 定时器：BullMQ delayed job，支持暂停 / 恢复
- 版本兼容：流程定义修改对运行中实例可配置策略（沿用旧版 / 升级到新版 / 手动选择），默认沿用旧版

### 8.3 关键不变量

- 同一实例同一时刻只有一个 `running` 节点
- 所有写操作在一个 DB 事务内，事务失败回滚 + 重试
- 审批人解析在节点进入时冻结，避免中途组织架构变更导致不一致
- 流程回退不删除历史，仅新增反向流转记录

## 9. 表单 / 页面 / 列表设计

### 9.1 Schema 格式

- 表单：`{ components: ComponentSchema[], dataModelRef, rules, fieldPerms }`
- 列表：`{ dataModelRef, columns, filters, sorts, viewType, pageSize }`
- 页面：`{ layout, components: ComponentSchema[], dataSources, actions }`
- `ComponentSchema`：`{ id, type, props, events, children?, bind? }`
- 绑定模型字段用 `bind: { entity, field, mode: 'read'|'write'|'hidden' }`

### 9.2 设计器架构

- `form-designer` / `page-designer` 基于 dnd-kit 的自由拖拽
- 左侧组件库 + 中间画布 + 右侧属性面板
- 表单设计器优先使用 formily（schema 标准化 + 校验生态）
- 页面设计器自研组件树，事件系统对齐 PRD 7.2.5

### 9.3 运行时

- `form-render` / `page-render` 同时支持设计器预览、桌面运行时、移动 H5
- 数据通过 `api-client` + React Query 拉取
- 权限由 `PermissionService` 在 `bind` 层注入，控制只读 / 隐藏
- 离线暂存：mobile 端用 IndexedDB 暂存未提交表单，恢复后按时间戳重放

### 9.4 JS 增强位

- 设计器提供受控的 "JS 增强" 面板，仅"高级搭建者"可见
- 运行时使用 `new Function` + 受限全局对象（不允许 `eval` / `Function` / `fetch` / `XMLHttpRequest` / `localStorage`）
- 沙箱由 `isolated-vm` 提供（Node 端），浏览器端用 Web Worker + postMessage 代理

## 10. 连接器架构

### 10.1 接口

```ts
interface Connector {
  type: 'http' | 'webhook' | 'mysql' | 'postgres' | 'email' | 'sms' | 'wecom' | 'storage';
  invoke(ctx: ConnectorContext): Promise<ConnectorResult>;
}
```

### 10.2 鉴权与脱敏

- 鉴权配置：API Key / OAuth2 / 数据库账密 / IM 机器人 webhook
- 字段在存储时使用 KMS 加密的引用（密钥由环境变量注入）
- 调试与日志展示自动脱敏（正则匹配手机号、身份证、token）

### 10.3 调度与可靠性

- BullMQ 队列 + 指数退避重试
- 超时可配（1–60s），默认 10s
- 失败上限后写入 `connector_alerts`，管理员可查
- 调用结果写 `connector_calls`，保留 90 天

### 10.4 触发器

- 流程节点类型 `Connector` 可调用连接器
- 连接器支持作为流程触发器（Webhook / 定时轮询）
- 定时轮询走 BullMQ repeatable job

## 11. 审计与可观测

### 11.1 审计

- 全量事件：`LOGIN` / `PERMISSION_CHANGE` / `DATA_*` / `WORKFLOW_*` / `CONNECTOR_CALL` / `APP_PUBLISH` / `EXPORT`
- 写入路径：业务操作完成后由拦截器统一写 `audit_logs`
- 写入走独立 BullMQ 队列，失败重试，避免阻塞主业务
- 敏感字段（身份证 / 手机号 / 银行卡 / token）写入时脱敏

### 11.2 可观测

- 日志：pino（结构化 JSON），输出到 stdout，由 Docker 收集
- 指标：`/metrics` 暴露 Prometheus 指标（HTTP 延迟、队列长度、流程实例数）
- 追踪：`traceId` 贯穿 HTTP header → 日志 → BullMQ job（MVP 阶段不开 OpenTelemetry，预留接口）
- 健康检查：`/healthz`（liveness）、`/readyz`（readiness，依赖 DB / Redis）

| --- | --- | --- | --- |

### 12.2 首次启动向导

- 访问 `http://localhost` → 检测到未初始化 → 引导设置管理员账号、站点名、上传 logo
- 完成后写入 `system_settings` 表，重启进入正常模式

### 12.3 升级与回滚

- 升级：`docker compose pull && docker compose up -d`
- 失败回滚：检测到 `server` 容器 unhealthy 自动 `docker compose down` 上一版本
- 数据迁移：启动时自动跑 Prisma migrate，失败阻塞启动

### 12.4 备份

- `backup` 容器每日凌晨 3 点 `pg_dump` 到 `/backups`
- 保留策略：近 7 天每日 + 近 4 周每周 + 近 12 月每月
- 恢复操作本身写审计

## 13. 性能与可扩展性

### 13.1 MVP 目标（与 PRD 8.4 对齐）

| 指标 | 目标 | 策略 |
| --- | --- | --- |
| 页面首屏 | ≤ 1.5s（P95） | Vite 构建 + 路由懒加载 + React Query 缓存 |
| 列表查询 | ≤ 1s（P95） | PostgreSQL 索引 + 分页上限 10000 |
| 流程审批 | ≤ 500ms（P95） | 仅写本地表，连接器走异步 |
| 单实例承载 | ≤ 100 应用 / 50 并发 / 10 万条 | 文档明确上限，集群模式留待 Phase 2 |

### 13.2 关键优化点

- 物理表必备索引：主键、外键、`created_at`、`updated_at`、`deleted_at`、列表筛选列
- 列表分页上限 10000，超量提示筛缩
- 大字段（附件、签名）走文件服务，不直接进库
- 流程实例表分区（按月），超过 100 万行后考虑归档

## 14. 安全

- HTTPS 由 Nginx 终结
- 内部 mTLS：MVP 阶段不启用，预留接口
- 密码 bcrypt cost 12
- 敏感字段（连接器密钥、个人敏感信息）落库前 AES-256 加密，密钥从环境变量注入
- 速率限制：Nginx limit_req + 应用层兜底
- CORS：默认同源，跨域需白名单
- CSP：web 端启用严格 CSP，禁 inline script（设计器预览态单独开）
- 文件上传：白名单 mime + 大小限制 + 病毒扫描（`[Hypothesis]` MVP 不集成 ClamAV）
